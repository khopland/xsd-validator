Compilation is expensive and bounded; validation is isolated per call. Schema identity and diagnostic indexes are prepared once, while document-specific state never crosses validation sessions.

03 / STRENGTHS

The implementation matches the promise

The strongest signal is consistency: README claims, API types, parser configuration, issue mapping, and tests reinforce one another.

Strong

Secure XML defaults

Secure processing is enabled, DOCTYPE is rejected, external entities and DTD loading are disabled, validation-time schema resolution is blocked, and compile-time dependencies default to local files.

Strong

Bounded schema materialization

Root and dependency byte caps, dependency-count and aggregate limits, exact-boundary tests, and an explicitly named trusted-unbounded escape hatch make the compilation trust boundary concrete.

Strong

Data minimization by construction

Public issues retain structure—not submitted lexical values. Tests exercise datatype, enumeration, attribute, fixed-value, identity, and entity cases and inspect both messages and report rendering for leakage.

Strong

Honest result semantics

Validity, parse completeness, issue truncation, wildcard coverage, and raw engine-event count remain separate. An incomplete parse cannot quietly masquerade as a valid document.

Strong

Stable, useful application contract

Nine compact public types expose immutable lists, JSpecify nullness, QName-aware indexed paths, stable issue codes, expected elements, schema identity, and explicit limits.

Strong

Release engineering discipline

Dependencies and plugins are pinned, GitHub Actions use commit SHAs, CI declares Java 17/21/25, release tags are validated, and binary, source, and Javadoc artifacts build successfully.

05 / FINDINGS

Risk now sits at the boundaries

There is no release-blocking defect in the reviewed tree. These are the highest-value next improvements, ordered by operational impact.

MED

Bound the total instance workload—or make upstream ownership explicit

ValidationLimits caps nesting depth and distinct child names, while diagnostics, retained siblings, attributes, and returned issues have fixed caps. It does not cap total bytes, character data, element count, or elapsed work. A document with very large text or many repeated same-name elements can therefore consume unbounded input and CPU. Add an element/character budget, offer a bounded-input helper, or state clearly that callers must provide a pre-bounded stream for untrusted documents.

EvidenceValidationLimits.java
Fixed retention caps
MED

Close the primary XML system-ID protocol gap

Schema-only system IDs are restricted to local files, but validation accepts a StreamSource or SAXSource containing only a system ID and passes it to the XML reader. External entity controls do not govern retrieval of the primary document itself. For applications that derive system IDs from untrusted input, this can become a network/file access boundary. Prefer supplied streams; consider rejecting non-file primary system IDs unless explicitly enabled.

EvidenceSchema restriction
Instance source handling
MED

Keep shrinking the Xerces compatibility blast radius

The new diagnostic adapter is a major improvement, but the runtime still depends on Xerces implementation types for the schema factory, error reporter, PSVI, grammar-pool access, structured keys, and argument positions. That coupling enables the library's best features; it also makes dependency upgrades unusually consequential. Add a representative golden diagnostic corpus and one narrow compatibility façade for all Xerces-specific casts and properties.

PSVI cast
LOW

Automate the assurance claims that are still manual

The POM has no coverage threshold, dependency-vulnerability/SBOM step, mutation testing, fuzzing, benchmark, or public-API compatibility check. For a parser-facing library, begin with informational JaCoCo and dependency scanning, then add targeted fuzzing for source handling and mapper fallbacks. Use Revapi or japicmp before the first 1.x release.

LOW

Resolve or intentionally suppress dependency-analysis noise

mvn dependency:analyze succeeds but reports the JUnit aggregate as unused and its API/params modules plus xml-apis as used-undeclared. Some of this is expected analyzer behavior, yet leaving it unresolved prevents the goal from becoming a useful CI guard. Configure explicit ignores or declare the precise JUnit modules so new dependency drift becomes visible.

07 / ACTIONS

A pragmatic sequence for 0.2

Preserve the current API clarity. Add controls and measurements around it rather than expanding the feature surface.

Document the instance trust boundary

State that untrusted XML should arrive through a caller-bounded stream and that a system ID may cause the primary document to be opened.

Add workload and protocol controls

Introduce total element/character budgets and an explicit opt-in for non-file primary system IDs.

Make compatibility observable

Capture a golden Xerces diagnostic corpus; add dependency scanning, API diffing, and informational coverage.

Retire stale review artifacts

Archive or regenerate the old 64-test report so repository documentation reflects the current 134-test tree.

Release view

Reasonable 0.2 release candidate

The tested core is coherent, immutable, defensive, and well documented. None of the findings requires an API redesign. The instance-source caveat should be documented before describing the library as safe for arbitrary untrusted sources.
